# Current architecture

**Scope:** This is an inventory of architecture that exists in the source tree. It describes code paths and ownership. For feature availability and validation results, see [current status](current-status.md). For the selected first-build scope, see [ADR 0001](adr/0001-single-account-desktop-email-client.md). [ARCHITECTURE.md](../ARCHITECTURE.md) is a historical proposal; its design recommendations are not evidence of implementation.

## Runtime and boundaries

The app has a Vue/TypeScript frontend, a Tauri 2 shell, and the Rust `mail-core` crate. The Rust crate owns persistence and provider operations. The frontend talks through a `MailClient` interface. In native mode, `createTauriMailClient` maps that interface to named Tauri commands. In browser mode, `browser-fake.ts` supplies a synthetic in-memory client. The shared interface and generated wire types are in [client.ts](../src/lib/ipc/client.ts), [tauri-client.ts](../src/lib/ipc/tauri-client.ts), [browser-fake.ts](../src/lib/ipc/browser-fake.ts), and [generated.ts](../src/lib/ipc/generated.ts). Rust DTOs are the source for generated TypeScript; `crates/mail-core/src/bin/generate-types.rs` generates the file.

The Tauri entry point in [main.rs](../src-tauri/src/main.rs) selects fixture or Gmail mode from configuration, opens the corresponding Rust store, registers command handlers, and emits mailbox/draft/close events. The webview does not access SQLite or provider HTTP directly. Its capabilities and generated command permissions are under [src-tauri/capabilities](../src-tauri/capabilities/main-window.json) and [src-tauri/permissions/autogenerated](../src-tauri/permissions/autogenerated).

## Rust state and transaction ownership

The fixture `MailCore` in [lib.rs](../crates/mail-core/src/lib.rs) owns a SQLite-backed `Store`, profile lock, change listeners, and a serial archive worker. [store.rs](../crates/mail-core/src/store.rs) owns fixture persistence and transaction logic. Command acceptance returns receipts after persistence; provider work is performed by a worker outside the acceptance transaction. Worker recovery and undo state are durable. The fixture provider is synthetic and does not connect to a mail service.

Gmail mode is implemented separately in [gmail/sync.rs](../crates/mail-core/src/gmail/sync.rs), [gmail/store.rs](../crates/mail-core/src/gmail/store.rs), [gmail/operations.rs](../crates/mail-core/src/gmail/operations.rs), and [gmail/provider.rs](../crates/mail-core/src/gmail/provider.rs). The sync service owns the Gmail cache and coordinates provider reads and queued operations. SQLite transactions persist local state; network calls occur through the provider path. OAuth flow, token access, and secret storage are in [gmail/auth.rs](../crates/mail-core/src/gmail/auth.rs) and [gmail/secrets.rs](../crates/mail-core/src/gmail/secrets.rs). The service exposes account status and sync state through DTOs. Runtime success on a supported macOS installation is a separate validation question; see [current status](current-status.md).

Drafts are stored in a separate `<selected-profile>/local-drafts` SQLite database by [drafts/store.rs](../crates/mail-core/src/drafts/store.rs), with revision and account identity types in [drafts/types.rs](../crates/mail-core/src/drafts/types.rs). The store uses WAL and FULL synchronous mode. Saves and deletes are revision-checked and return receipts after commit; deletion records request tombstones so a late save cannot recreate a removed draft. The frontend draft composable and editor coordinate local edits, acknowledged saves, and error recovery in [useDrafts.ts](../src/composables/useDrafts.ts), [DraftEditorCore.vue](../src/components/DraftEditorCore.vue), and [ReplyComposer.vue](../src/components/ReplyComposer.vue). Drafts remain local to the profile and do not sync to Gmail.

The native close path uses a request/acknowledgement gate in [close_gate.rs](../src-tauri/src/close_gate.rs). The shell asks the frontend to flush and close dirty draft state; the frontend acknowledges only after the latest save is committed, and cancels close when save fails. Frontend coordination lives in [App.vue](../src/App.vue) and the draft composable. The governing contract is [vertical slice 04](vertical-slice-04.md).

## Frontend coordination

[App.vue](../src/App.vue) is the composition root for navigation, focused conversation, panels, and mailbox actions. [useMailbox.ts](../src/composables/useMailbox.ts) owns account-scoped focus and mailbox query coordination. Components render the inbox, reader, composer, activity, and account controls. The client subscription events are invalidation hints; the frontend reloads through client queries.

The production native client and browser fake share the same `MailClient` contract, but they do not share persistence or provider behavior. Browser tests and preview use the fake client; they cannot establish native SQLite, OAuth, OS keychain, system dialogs, or WKWebView behavior. The boundary and runtime checks are recorded in [development guidance](development.md) and [current status](current-status.md).

| Reminders | Rust stores account-scoped local reminder records in [reminders.rs](../crates/mail-core/src/reminders.rs); fixture reminders use a synthetic archive/restore path, while Gmail reminders remain device-local and do not mutate Gmail. Frontend time handling, preferences, and panels are in [reminder-time.ts](../src/lib/reminder-time.ts), [reminder-preferences.ts](../src/lib/reminder-preferences.ts), and [RemindersPanel.vue](../src/components/RemindersPanel.vue). | [UX-11](ux-11-local-reminders.md) |

Gmail retrieval is authenticated and read-only; fixture mode exposes a synthetic text attachment. The shell mediates explicit transfers to a fixed OS Downloads destination in [main.rs](../src-tauri/src/main.rs). The UI chooses from descriptors and tracks transfer state in [useAttachmentTransfer.ts](../src/composables/useAttachmentTransfer.ts); it has no arbitrary file picker. | [UX-12](ux-12-safe-attachments.md) |
| Draft lifecycle | Rust owns local draft persistence and revision checks. Vue owns editor buffers and save coordination. | [Vertical slice 04](vertical-slice-04.md) |
| Synthetic workspaces | [fixture-workspaces.ts](../src/lib/fixture-workspaces.ts) creates two separate browser-fake clients with distinct account identities; IDs may overlap. These are not connected multi-account support. | [UX-13](ux-13-independent-workspaces.md) |

Durable bulk-action acceptance and undo are owned by [groups.rs](../crates/mail-core/src/groups.rs) and the fixture/Gmail operation stores. Cached Done and Trash browsing projections are separate: [cached_done.rs](../crates/mail-core/src/cached_done.rs) and [cached-trash.ts](../src/lib/cached-trash.ts). See contracts [UX-04](ux-04-trustworthy-undo.md), [UX-05](ux-05-safe-bulk-processing.md), and [UX-10](ux-10-bounded-triage.md).

## Design proposals and limits

The source tree does not make every proposal in [ARCHITECTURE.md](../ARCHITECTURE.md) current behavior. In particular, do not infer full multi-account/provider support, provider-synced drafts, fully quit background sync, arbitrary provider search coverage, or live macOS runtime validation from the existence of interfaces or tests. [ADR 0001](adr/0001-single-account-desktop-email-client.md), the slice contracts, feature contracts, and [current status](current-status.md) define scope and validation. New architecture recommendations belong in an explicitly labeled proposal or ADR, separate from this source inventory.
