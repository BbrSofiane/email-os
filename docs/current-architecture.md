# Current architecture

**Scope:** This is an inventory of architecture that exists in the source tree. It describes code paths and ownership. For feature availability and validation results, see [current status](current-status.md). For the selected first-build scope, see [ADR 0001](adr/0001-single-account-desktop-email-client.md). [ARCHITECTURE.md](../ARCHITECTURE.md) is a historical proposal; its design recommendations are not evidence of implementation.

## Runtime and boundaries

The app has a Vue/TypeScript frontend, a Tauri 2 shell, and the Rust `mail-core` crate. The Rust crate owns persistence and provider operations. The frontend talks through a `MailClient` interface. In native mode, `createTauriMailClient` maps that interface to named Tauri commands. In browser mode, `browser-fake.ts` supplies a synthetic in-memory client. The shared interface and generated wire types are in [client.ts](../src/lib/ipc/client.ts), [tauri-client.ts](../src/lib/ipc/tauri-client.ts), [browser-fake.ts](../src/lib/ipc/browser-fake.ts), and [generated.ts](../src/lib/ipc/generated.ts). Rust DTOs are the source for generated TypeScript; `crates/mail-core/src/bin/generate-types.rs` generates the file.

The Tauri entry point in [main.rs](../src-tauri/src/main.rs) selects fixture or Gmail mode from configuration, opens the corresponding Rust store, registers command handlers, and emits mailbox/draft/close events. The webview does not access SQLite or provider HTTP directly. Its capabilities and generated command permissions are under [src-tauri/capabilities](../src-tauri/capabilities/main-window.json) and [src-tauri/permissions/autogenerated](../src-tauri/permissions/autogenerated).

## Rust state and transaction ownership

The fixture `MailCore` in [lib.rs](../crates/mail-core/src/lib.rs) owns a SQLite-backed `Store`, profile lock, change listeners, and a serial archive worker. [store.rs](../crates/mail-core/src/store.rs) owns fixture persistence and transaction logic. Command acceptance returns receipts after persistence; provider work is performed by a worker outside the acceptance transaction. Worker recovery and undo state are durable. The fixture provider is synthetic and does not connect to a mail service.

Gmail mode is implemented separately in [gmail/sync.rs](../crates/mail-core/src/gmail/sync.rs), [gmail/store.rs](../crates/mail-core/src/gmail/store.rs), [gmail/operations.rs](../crates/mail-core/src/gmail/operations.rs), and the Gmail provider modules. The sync service owns the Gmail cache and coordinates provider reads and queued operations. SQLite transactions persist local state; network calls occur through the provider path. [gmail/provider.rs](../crates/mail-core/src/gmail/provider.rs) owns HTTP, credentials, pacing, status, and quota handling; [gmail/provider/api.rs](../crates/mail-core/src/gmail/provider/api.rs) implements the `GmailProvider` trait (auth/session, reads and writes; defined in [gmail/types.rs](../crates/mail-core/src/gmail/types.rs)) for the concrete `LiveGmailProvider`; [gmail/parse.rs](../crates/mail-core/src/gmail/parse.rs) contains pure Gmail response and message parsing. OAuth flow, token access, and secret storage are in [gmail/auth.rs](../crates/mail-core/src/gmail/auth.rs) and [gmail/secrets.rs](../crates/mail-core/src/gmail/secrets.rs). The service exposes account status and sync state through DTOs. Runtime success on a supported macOS installation is a separate validation question; see [current status](current-status.md).

Gmail schema upgrades are owned by `gmail/store_schema.rs`. The authoritative
`meta.schema_version` advances through `gmail-migrations-1` to
`gmail-migrations-9`, with each stage's DDL, backfills and marker in one
transaction. Pre-numbered `gmail-1` and `gmail-2` profiles had ambiguous physical
layouts, so only those historical migration bodies inspect optional columns.
An already-current profile performs no migration writes. Fresh profiles use the
canonical schema captured from the pre-change store. Unknown or newer markers
fail before schema changes. Startup crash recovery runs explicitly after
migration: globally applying operations become uncertain and lose `last_error`.
Reconnect recovery remains account-scoped and additionally clears `failure`;
these distinct semantics are preserved.

`GmailStore` stays one type owning the single SQLite connection; its impl and
helpers are split by responsibility under `gmail/store/`. `store.rs` holds the
shared types and the struct; every method that opens a transaction still opens
exactly one, so acceptance and reconciliation keep their atomic scope.

| Module | Responsibility |
| --- | --- |
| `profile` | open and startup recovery, account identity, generation, sync checkpoints, disconnect cleanup, saved split |
| `cache`, `cache_rows` | cached conversation reads; thread and fact upserts, eviction, conversation building, `meta` helpers |
| `ingestion` | discovery and history pages, rediscovery |
| `search`, `search_support` | cached search, done, trash and starred lists; search admission and eviction |
| `acceptance`, `operation_rows` | single-operation acceptance and retry; acceptance transaction, preimages, operation row codecs |
| `worker` | claim, confirm, reconcile, defer, requeue and finish |
| `undo`, `undo_support` | single-operation undo and its compensation helpers |
| `group_acceptance`, `group_queries`, `group_undo`, `group_rows` | group acceptance, status queries, group undo and the shared group row helpers |
| `activity` | effective conversation state and the activity list |
| `reminders`, `destinations` | local reminders; destination snapshots |

Store tests live in `gmail/store_tests.rs` beside `migration_tests.rs`.

Storage failures are diagnosable without leaking data. Every storage failure
still reaches the wire as `MailError::StorageUnavailable`, unchanged, but the
point that produced it first logs exactly one line through the `log` facade:
the call site's `file:line`, a static cause tag (`sqlite`, `lock_poisoned`,
`thread_join`, `path_unavailable`, `missing_persisted_row` and similar) and,
for SQLite errors, the primary result code name and extended code. The line
is built only from static strings and numbers; the Display text of the
underlying error is never read, because SQLite messages can quote values and
SQL. `mail-core` owns the helper in [storage_log.rs](../crates/mail-core/src/storage_log.rs);
the shell has its own small helper and the stderr logger in
[diagnostics.rs](../src-tauri/src/diagnostics.rs), which passes only the two
storage log targets and drops everything else. Re-mapping an error that was
already a `MailError` does not log a second time. Rejections because the sync
worker is stopped or halted are not logged: the failure that halted it already was.

Drafts are stored in a separate `<selected-profile>/local-drafts` SQLite database by [drafts/store.rs](../crates/mail-core/src/drafts/store.rs), with revision and account identity types in [drafts/types.rs](../crates/mail-core/src/drafts/types.rs). The store uses WAL and FULL synchronous mode. Saves and deletes are revision-checked and return receipts after commit; deletion records request tombstones so a late save cannot recreate a removed draft. The frontend draft composable and editor coordinate local edits, acknowledged saves, and error recovery in [useDrafts.ts](../src/composables/useDrafts.ts), [DraftEditorCore.vue](../src/components/DraftEditorCore.vue), and [ReplyComposer.vue](../src/components/ReplyComposer.vue). Drafts remain local to the profile and do not sync to Gmail.

The native close path uses a request/acknowledgement gate in [close_gate.rs](../src-tauri/src/close_gate.rs). The shell asks the frontend to flush and close dirty draft state; the frontend acknowledges only after the latest save is committed, and cancels close when save fails. Frontend coordination lives in [App.vue](../src/App.vue) and the draft composable. The governing contract is [vertical slice 04](vertical-slice-04.md).

## Frontend coordination

[App.vue](../src/App.vue) is the composition root for navigation, focused conversation, panels, and mailbox actions. [useMailbox.ts](../src/composables/useMailbox.ts) owns account-scoped focus and mailbox query coordination and keeps the public `Mailbox` shape. It composes focused modules that receive their dependencies as arguments rather than closing over the parent: [useMailboxSelection.ts](../src/composables/useMailboxSelection.ts) owns the UX-05 selection set, range anchor and `SELECTION_MAX` bound (the parent clears it on context, account and saved-view invalidation and prunes it after each authoritative list read), [useMailboxGroups.ts](../src/composables/useMailboxGroups.ts) owns UX-05 group dispatch, the single group notice, lost-response recovery on the original request id, partial group Undo, restart notice rehydration and the Activity group history/detail reads, [useMailboxDetailCache.ts](../src/composables/useMailboxDetailCache.ts) owns the bounded neighbor-detail cache, its TTL, the single-slot prefetch and the J/K reader loading delay (its fence is an epoch the owner bumps through `invalidateDetailCache()` on every refresh, mutation start, reader close, account change and disconnect), and [mailbox-refs.ts](../src/composables/mailbox-refs.ts) and [mailbox-session.ts](../src/composables/mailbox-session.ts) hold the shared conversation-reference helpers and the session/command-fence types. Session invalidation is an explicit argument: `useMailbox` owns the session counters and hands extracted pieces a read-only `MailboxSession` (generation and detached flag) plus the shared command fence; each async path captures the generation before its first await and drops its result when it moved. Components render the inbox, reader, composer, activity, and account controls. The client subscription events are invalidation hints; the frontend reloads through client queries.

The production native client and browser fake share the same `MailClient` contract, but they do not share persistence or provider behavior. Browser tests and preview use the fake client; they cannot establish native SQLite, OAuth, OS keychain, system dialogs, or WKWebView behavior. The boundary and runtime checks are recorded in [development guidance](development.md) and [current status](current-status.md).

## Validation task boundaries

The `mise run check` task serially runs headless core tests, the generated IPC contract check, core formatting and clippy, frontend tests, and frontend typechecking. It does not require GTK/WebKit development packages. Native shell clippy, bridge tests, and the web production build are separate tasks; `mise run check:all` runs the full sequence, including `lint:native`, serially after native prerequisites are installed. CI installs Linux prerequisites before running this full gate. Rendered Chromium suites remain opt-in and are not part of CI.

## Design proposals and limits

The source tree does not make every proposal in [ARCHITECTURE.md](../ARCHITECTURE.md) current behavior. In particular, do not infer full multi-account/provider support, provider-synced drafts, fully quit background sync, arbitrary provider search coverage, or live macOS runtime validation from the existence of interfaces or tests. [ADR 0001](adr/0001-single-account-desktop-email-client.md), the slice contracts, feature contracts, and [current status](current-status.md) define scope and validation. New architecture recommendations belong in an explicitly labeled proposal or ADR, separate from this source inventory.
