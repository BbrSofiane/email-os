# ADR 0002: Fixture mode as a synthetic provider

**Status:** Proposed

## Question and recommendation

Investigate replacing the native fixture store/worker with `GmailCore` and a built-in, credential-free `SyntheticProvider`. This is a decision spike, not authorization to change production behavior. Baseline: `58e0bc7`.

**Recommendation: GO for staged unification; NO-GO for an unmodified provider-only substitution.** GmailCore already accepts `Arc<dyn GmailReadProvider>` and an injected clock. The provider must own durable synthetic provider facts; the core needs a small explicit fixture policy for mode/capabilities/lifecycle and reminders. Keeping a second operation ledger is avoidable, but silently changing the fixture contract is not acceptable. After those gates, delete the fixture `Store`, worker, reminder implementation and `MailCore` facade, and hold one `GmailCore` in shell state with a session policy instead of the `Backend` enum. Move the 18-conversation data out of `seed.rs` into the synthetic module before deleting that file. Retain shared `CancelToken` infrastructure currently located in `provider.rs`; removing the old archive fake must not remove Gmail cancellation support.

## Evidence checkpoints

- Required architecture, status, development and ADR 0001 read. Current docs explicitly promise a separate durable native fixture profile, seed-once behavior, archive-only mailbox actions, local drafts and synthetic attachment transfers.
- `gmail/sync.rs::open_with_clock` has no direct OAuth/Keychain dependency: those belong to the injected production `GmailProvider`. Startup currently interprets `has_credentials()` as a restore signal; a synthetic implementation needs an explicit local-ready policy rather than inventing real credentials.
- `gmail/sync.rs::account_status` hardcodes `MailMode::Gmail`; `mutation_access()` is a Boolean grant covering archive/read/star. Neither preserves fixture wire behavior by itself.
- All requested fixture test files were inventoried by test function name (appendix below). No production files are changed by this spike.

## Implementation stages (each must remain green and shippable)

1. Port fixture-specific guarantees to tests against GmailCore, retain both existing backends, and add a production synthetic data/provider module independent of test support. Keep the default fixture path unchanged.
2. Introduce explicit internal session policy in GmailCore: fixture identity/status, archive-only admission, unsupported errors, cached-only search, local readiness and non-destructive lifecycle. Implement persistent synthetic provider facts and seed-once discovery including the two initially archived conversations. Keep Gmail policy unchanged.
3. Resolve reminder behavior explicitly and cover it with acceptance/race/restart tests; move synthetic attachments/reply metadata behind provider/core seams. Preserve local drafts and fixture profile safety. Add opt-in synthetic-core launch path for validation.
4. Switch fixture default only after all mapped guarantees pass and profile transition disclosure is implemented. Keep the old database as backup. Remove the legacy backend after parity validation; update current docs and browser contract tests. Coordinating thread owns end-to-end validation and merge sequencing.

## Risks and decision gates

A fresh provider seeded into memory on every launch can overwrite archived provider facts at the next sync. Gmail discovery only lists Inbox, so it cannot by itself reproduce the two archived seed threads. GmailCore may expose read/star or destructive disconnect if fixture mode is represented as Gmail. Reminder scheduling currently has different mailbox effects. These are design gates for implementation, not bugs established by this spike.

The prototype will be published separately at [maintenance/p4-synthetic-provider-prototype](https://github.com/BbrSofiane/email-os/tree/maintenance/p4-synthetic-provider-prototype), marked throwaway and not for merge. This PR contains only this ADR.

## On-disk transition

Today startup selects `<app_data>/fixture-profile/mail.db`; `Store::migrate_and_seed` owns fixture schema versions through 4 and seed version 1. GmailStore opens `gmail.db` with unrelated tables/migrations. Opening that new file beside `mail.db` is not a migration. `docs/development.md` promises seeds never reset provider facts or operation history; `docs/current-status.md` promises durable synthetic state and drafts. A silent reset violates that promise.

Choose **reset with disclosure and retained backup**, not an operation-ledger migration, for the eventual implementation. Before changing fixture storage, show a one-time explicit disclosure that synthetic mailbox actions, history, reminders and saved split start fresh; do not automatically approve or execute it as part of this ADR. Keep old `mail.db` and its journal/WAL state safely backed up under the profile lease using a consistent SQLite backup, not a live raw file copy. Record the transition atomically so crashes cannot repeatedly reset the new profile. Never apply this transition to `gmail-profile` or credentials. The implementation must cover cancel, crash/restart, insufficient disk and backup failure before switching.

Retain `<fixture-profile>/local-drafts` untouched, along with its account identity and fixture mailbox, so draft references to fixed conversation/message IDs remain meaningful. Do not recursively delete the fixture directory. Test opening old drafts and reply source references after the new seed bootstrap. Update development/status/fixture documentation to state the one-time reset; thereafter retain seed-once/restart persistence. A migration preserving pending preimages/groups/reminder revisions would cost more and needs its own mapping; this proposal deliberately does not promise it.

## Wire and frontend contract

No DTO shape, generated TypeScript definition, IPC command name or event name needs to change. `dto.rs`, `gmail/types.rs`, `groups.rs`, `reminders.rs`, `src/lib/ipc/client.ts`, `tauri-client.ts` and `generated.ts` can remain the wire source of truth. This spike changes none. A naive switch would change **values and errors** visible on that wire: mode, grant, connection/sync state, coverage count, unsupported command errors and reminder phases. The staged policy must preserve the former values/errors, with the explicitly disclosed local-reminder and initial-loading adjustment above; run generated-contract checks even if no DTO edit is expected.

`src/composables/useMailbox.ts` uses mode and mutation access for Gmail upgrade/action controls. `src/lib/browsing-actions.ts` and browser fake controls model Gmail stars/destinations separately. `src/lib/ipc/browser-fake.ts` defaults to fixture, seeds in-memory synthetic conversations, implements simulated-Gmail mode/grants, uses `fixture-text` attachments, fake reply metadata and in-memory operation/reminder ledgers. `fixture-workspaces.ts` also permits overlapping IDs across two isolated synthetic accounts. It remains a browser implementation, not a production provider dependency. Frontend/browser tests establish capability gating, identities, error/receipt rendering, deterministic selection and fake timers; they do not establish SQLite durability, OAuth or native provider behavior. Preserve their fixture/default assumptions and add boundary tests for synthetic native status; do not relabel every browser fixture as Gmail to make tests pass.

## Size, risk and fallback

Measured source sizes at baseline: fixture `store.rs` 4,030 lines (2,647 before unit tests), `worker.rs` 200, `seed.rs` 327, `provider.rs` 211, fixture `store/reminders.rs` 341; reminder unit/race files 377 combined. Those five principal files total **5,109 lines**, including embedded tests/data; seed data and cancellation infrastructure must move rather than vanish. `lib.rs` is 630 lines (facade/test portions removable, public shared modules remain); the shell Backend implementation occupies about 380 lines plus subscription variants. Including removable facade/shell forwarding, roughly **4,000–4,500 non-test lines removed or replaced**, and roughly **5,000–6,000 gross lines** including relocated tests/data; do not present gross deletion as net savings.

Planning estimate, not a prototype diff: add/retain 500–900 lines of production synthetic data/provider persistence, 150–350 lines of session policy/bootstrap and 150–300 lines of transition/disclosure logic, plus 500–1,200 lines of ports/contract tests. Reminder policy work may exceed this. Net production reduction is plausibly 1,000–2,000 lines, contingent on review. Removing 23 duplicated group/undo helpers (~730 lines) is a concrete payoff, not proof the whole rewrite is cheap. Main risks are synthetic facts being overwritten on restart; archived seeds omitted; grants accidentally broadened; reminder semantic drift; draft loss from broad reset; crash-safe backup; shared-core regressions in Gmail; and a long migration with two enabled paths. Each stage must retain working defaults and pass targeted core, contract and native bridge checks; final UI/end-to-end gates belong to the coordinator.

If the policy/bootstrap/reminder cost becomes unacceptable, **no-go fallback**: keep both stores and extract only the duplicated ledger algorithms. Define a private `OperationLedgerStorage` seam over an already-owned transaction: load operation/preimage/group rows, enumerate ordered members and newer intent, persist undo decisions/links/receipts, and insert compensation. Shared typed structs carry operation status/dimension/targets, while each adapter owns SQL/table/column names (`operations` vs `gmail_operations`, `failure_kind` vs `last_error`) and row conversion. Pass Clock/now explicitly. Transaction ownership, admission, provider execution, reconciliation and reminder semantics stay in each store; avoid a generic SQL string interpolation framework. Port both existing test matrices before removing helpers. Estimate 250–450 lines of adapters and 100–200 of shared types/glue replacing ~730 duplicated lines (modest net saving), plus a small shell error-policy helper with explicit compatibility tests. It has lower migration risk and no profile reset, but leaves two workers/facades/reminder paths and most shell forwarding. It is a viable smaller ticket if full unification fails its parity gates.

## Prototype evidence and limits

The separate [throwaway prototype branch](https://github.com/BbrSofiane/email-os/tree/maintenance/p4-synthetic-provider-prototype) contains only additive test code, based on `58e0bc7`; it is **not for merge**. It constructs `SyntheticProvider` directly and runs real GmailCore/GmailStore SQL, using the repository's actual seed via a test-local path import. There is no Google HTTP client, credentials store, OAuth or Keychain construction. `has_credentials() = true` is a readiness shim that selects startup restore; it does not represent a token. `mutation_access() = true` enables the experiment's archive operations and demonstrates why production needs the separate archive-only policy.

Ordinary discovery gives the correct 16-row Inbox. The harness explicitly preloads the two archived seed conversations through `load_search_conversation`; cached search then lists all 18 and the reader checks every fixed ID/subject/message count with the original Inbox facts. The remaining flows use a frozen injected clock: confirmed single archive then compensating Undo; confirmed two-member archive group then group Undo; shutdown and reopen with a **new provider object** reading its saved facts; replay of the same durable SQLite acceptance receipt; and a future local reminder that hides locally then returns after clock advancement. The timer experiment follows Gmail reminder rules, not fixture archive/restore phases.

Special cases still required before production: move seed data into a normal production module; make provider facts transactional/crash-durable (the prototype uses non-atomic JSON and defaults missing/malformed JSON to seed facts); model archive per message rather than per conversation; replace readiness/grant shims with explicit fixture policy; replace full-catalog history replay with stable synthetic change tracking; preserve fake pause/reject cancellation semantics; populate synthetic attachments/reply metadata; implement profile transition and port the remaining guarantees below. No test-support feature is enabled or imported. This is evidence that the existing ledger can serve synthetic mail, not evidence of full fixture parity or Gmail/platform correctness.

Validated prototype head [`0d6c482daee125c8246daf822db46067fbea6b37`](https://github.com/BbrSofiane/email-os/commit/0d6c482daee125c8246daf822db46067fbea6b37): `CARGO_TARGET_DIR=/home/exedev/email-os/target cargo test -p mail-core --test synthetic_provider_spike` — **1 passed, 0 failed**. The one integration test runs every flow above; it is not the full regression suite. Only warning: the path-imported seed module has an unused `SEED_VERSION`. Targeted Rust work was serialized after checking the sibling build slot; no frontend suite or broad Rust build was run for this spike. Production sources, DTOs and lockfile remain unchanged. `git diff --check` passed for the ADR.
