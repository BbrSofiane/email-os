<result>**1. Testing status, External user type**

- Expiry: "Authorizations by a test user will expire seven days from the time of consent. If your OAuth client requests an `offline` access type and receives a refresh token, that token will also expire." (https://support.google.com/cloud/answer/15549945)
- The developer docs say the same for refresh tokens: a "Testing" project "is issued a refresh token expiring in 7 days." (https://developers.google.com/identity/protocols/oauth2#expiration)
- Scopes: the only exception is when the app requests "a subset of the following: name, email address, and user profile" (`userinfo.email, userinfo.profile, openid`). "If your app requests any other OAuth scopes, then this exception does not apply." (https://support.google.com/cloud/answer/15549945). Gmail scopes therefore get the 7-day rule.
- Test user cap: "limited to up to 100 test users listed in the OAuth consent screen." (https://support.google.com/cloud/answer/15549945)

**2. In production, unverified, Gmail restricted scopes**

- Screen: "The app or script might display an 'unverified app' screen before it displays the consent screen." (https://support.google.com/cloud/answer/7454865)
- User cap: "100 new users in total, after the app presents the unverified app screen." The cap "applies over the entire lifetime of the project, and it cannot be reset or changed." (https://support.google.com/cloud/answer/15549945)
- Expiry: Google does not say whether tokens expire in this state. The 7-day rule appears only in the "Testing" text on the pages above. The production text on https://support.google.com/cloud/answer/15549945 does not mention it. The general expiry list at https://developers.google.com/identity/protocols/oauth2#expiration includes "The refresh token has not been used for six months" and "The user changed passwords and the refresh token contains Gmail scopes," but nothing about a 7-day limit outside Testing.

**3. Personal use / developer-only exemption**

- Google's verification-exception text (https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification, the "Personal use" section; I did not fetch the 13464321 URL directly): "One use case is if you are the only user of your app or if your app is used by only a few users, all of whom are known personally to you." It adds that these users "might be comfortable with advancing through the unverified app screen." A user cap still applies to this case.
- Separately, "Personal mode" (https://support.google.com/cloud/answer/15549945) is a different thing. It is a project type chosen at setup: "Personal mode apps do not require OAuth app verification, are not subject to the OAuth user cap or 7-day test user token expiration, and do not display the unverified app screen." It is one-time: "once a project is configured with a user type of Personal, it cannot be changed to External or Internal, and existing External or Internal applications cannot be switched to Personal." Personal mode is restricted to the creator: "client_user_mismatch" error otherwise.
- Also, "Apps in development" need no verification "unless you decide to launch it to the public" (https://support.google.com/cloud/answer/7454865).

**4. "Blocked" vs "not verified"**

- The pages I read describe warnings and limits, not a block. The wording is "Google hasn't verified" (alt text in https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification) and "the unverified app screen" (https://support.google.com/cloud/answer/7454865).
- Unverified apps face "a warning message ... in order to prepare your users for potential loss of functionality," and then "will be limited to 100 new users until it is verified." (https://support.google.com/cloud/answer/7454865)
- The 7454865 page includes an image titled "Sign in with Google temporarily disabled window" in the user-cap section. That is only an image title, with no text explaining when it appears.
- I found no page that quotes an "This app is blocked" message. The "org_internal" and "client_user_mismatch" errors are documented, but they relate to Internal and Personal projects.
