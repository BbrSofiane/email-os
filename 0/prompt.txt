## Decisions already made

The ADR is merged with Status "Proposed". The project owner asked for the remaining tickets to run, and I am proceeding on these decisions. In your first PR, record them in the ADR under a short "Decisions" section and change the status to "Accepted (stages 1–3)". Word it accurately: these were taken on the coordinator's recommendation, and the owner can still redirect before stage 4.

1. Go with staged unification, as the ADR recommends.
2. Synthetic fixture mode admits archive, read and star (single and group), and the cached Starred list works. This departs from the ADR's "archive-only" wording, which was about preserving today's errors; the decision is that the unified fixture gains read and star. 4. The on-disk transition (stage 4) will be a one-time reset with disclosure and a retained backup, local drafts untouched. You do not implement it; you plan it.

Everything else in the ADR's table stands: wire mode stays `fixture`, the account stays `fixture-account`, no OAuth, no Keychain, no HTTP client, cached-only search, all 18 conversations present including the two initially archived ones (`conv-06`, `conv-15`), the fake pause/reject environment controls apply only to synthetic writes and never reach the live provider.

## The three stages, one PR each

Stack the branches (`maintenance/p4-synthetic-stage1`, `-stage2`, `-stage3`). The stage 1 PR targets `main`; the others target the branch below. CI only runs on PRs whose base is `main`, so each stage must pass `mise run check:all` locally before you mark its PR ready. Open each PR as a draft and mark it ready when green. Message me when each one is ready.

**Stage 1 — port the guarantees, add the provider.**
- Record the decisions in the ADR (above).
- Production synthetic data module and `SyntheticGmailProvider` implementing `GmailProvider`, constructed directly, with durable facts.
- Port the fixture guarantees to tests that run against `GmailCore` + the synthetic provider, following the ADR appendix test by test. Keep a table in the PR description: each appendix entry → the new test, or "obsolete under decision N", or "deferred to stage 2/3 because …". Nothing silently dropped.
- Fix known divergence KD-3 on the fake's side: undo on a group whose members are all ineligible is accepted by both Rust stores with members marked skipped, and rejected by the browser fake with `not_applicable`. Align the fake to Rust, remove the `KNOWN_DIVERGENCES` entry (the runner tells you if an entry no longer fails), and keep that in its own commit.

**Stage 2 — explicit session policy and seeding.**
- An explicit internal session policy in `GmailCore` (not a scattering of `if fixture` checks): identity and status (`fixture` mode, `fixture-account`, connected/idle presentation per the ADR table, no mutation "grant" masquerading as a Google permission), admission (decision 2), lifecycle rejections, cached-only search, local readiness in place of the `has_credentials()` restore signal, and non-destructive lifecycle. Gmail's policy is the existing behaviour, unchanged.
- Seed-once bootstrap that finishes before the session reports ready, including the two initially archived conversations, without pretending they are Inbox mail. Initially archived rows are not Done evidence.
- No needless periodic synthetic discovery, or make a stable empty history cheap. Fake pause/reject must not stall reads or bootstrap.
- Add a `synthetic` profile to the Rust contract scenario runner and run every scenario on it. It should match the `gmail` profile except where the policy says otherwise; any difference is either a named, justified entry or a bug you fix. KD-2 (fixture `setRead` errors) concerns the old `fixture` profile and stays listed until stage 4; note in the PR what the fake will need at stage 4.

**Stage 3 — reminders, attachments, reply metadata, opt-in launch.**
- Reminders on the synthetic session under the Gmail local rules, with acceptance, race and restart tests (injected clock). Fresh reads come from the durable synthetic provider.
- The synthetic `fixture-text` attachment (same descriptor, filename, exact bytes, limits, exact-target revalidation, cancellation) and deterministic reply metadata (including the hostile literal bodies, sender identity and references) served through the provider/core seams rather than fabricated in the shell. The shell's transfer security stays common. The old shell path keeps working for the default backend.
- An opt-in launch path: an environment variable (suggest `EMAIL_OS_SYNTHETIC_CORE=1`, fixture mode only, ignored in Gmail mode) that makes the shell run fixture mode on `GmailCore` + the synthetic provider with its own database file under the fixture profile. `local-drafts` is shared and untouched, `mail.db` is never opened for writing on this path. Document it in `docs/development.md` as a validation path, not a user feature. I will run my native smoke test on it, so the 18 conversations, archive, undo, reader, search, drafts and reminders must work end to end through the real Tauri commands. Add native bridge tests in `src-tauri` for it.
