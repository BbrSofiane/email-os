## PR 1: minimum window width so 200% text cannot overflow the Inbox row
Branch `maintenance/followups-min-width` (your worktree's branch), base `main`.

**Background.** PR #57's description has the measurements (read it: `gh pr view 57 -R BbrSofiane/email-os`). In the worst-case row (old date, unknown read state, held unarchive) the compact Inbox row fits up to a 30.25px root font at 1000px wide and up to 36.5px at 1100px. So 32px text (200%) overflows by 27px at 1000px. The window opens at 1100px (`src-tauri/tauri.conf.json`) and has no minimum width. The owner chose: keep the row as it is and add a minimum window width, rather than tighten the documented 12px gaps or lower the sender/subject floors.

**Do.**
1. Measure, in the rendered harness (`tests/browsing/inbox-list.rendered-layout.test.ts`, real Chrome), the smallest width at which the worst-case compact row has zero overflow at a 32px root font. My interpolation says about 1030px; treat that as a guess.
2. Set `minWidth` on the main window in `src-tauri/tauri.conf.json` to that width plus a margin, rounded to a tidy number. The native webview is WebKit, not Chrome, and nobody has measured it there, so the margin is the allowance for that: state the measured bound and the margin you chose. Do not exceed the 1100px default width.
3. Add a rendered test step that reads `minWidth` from `src-tauri/tauri.conf.json` and asserts the worst-case row does not overflow at that width with a 32px root font, so the config and the layout cannot drift apart. It must fail if `minWidth` is lowered to 1000.
4. Record the decision in `DESIGN.md` beside the existing large-text checkpoints ("Type scale and dates").
5. Check whether a minimum height is already implied anywhere; do not add one unless a test needs it. Do not change any CSS in this PR.

In the PR description say what is not covered: tiling window managers may ignore a minimum size, Android is unaffected, WebKit is unmeasured.
