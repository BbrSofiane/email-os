## Findings

**1. BUG (medium) – `crates/mail-core/src/gmail/sync.rs:2123-2125`, `:2196`, `:2223`**
- **Scenario:** A group archive queues N operations and the first one fails definitely (`fail_next` gives `ProviderRejected`, so `run_one` returns `Err` and the outcome is `SyncError`).
  - The Mutations pass cleared `operations_requested` when it was selected (`:2121`). Only a `Complete` pass re-arms it from `more_claimable_mutations` (`:2196`).
  - On Gmail, the next 60 s periodic `Sync` completes and sets `operations_requested = true`, which drains the siblings. That is the "next retry tick" that KD-1 in `contract_scenarios.rs:53` refers to.
  - With `periodic_sync()` false, nothing re-arms it. Siblings stay `queued` until the user makes another write or reopens. The legacy fixture drained them, so this is a regression for the fixture.
- **Also affects:** any `requeue_operation` path, such as a wrapped provider whose `mutation_access` disagrees with the policy, and `outcome_unknown` rows deferred with `last_error`.
- **The KD-1 text for the synthetic profile is wrong.** It says "same cause as the gmail profile", but the "until next retry tick" premise no longer holds, so the stall is permanent.
- **Fix:** keep the tick, but make a due tick in a synthetic session re-arm the operations pass instead of running Sync.
  - In the `else` branch, when `tick_due &amp;&amp; !policy.periodic_sync()`, set `st.operations_requested = true`. Do not add an immediate retry on `SyncError`, because a persistently failing operation would then spin.
  - Keep the `sync_deadline = now + worker_wait(backoff_delay(..))` reset in that branch. An `Idle` pass does not reschedule, so omitting it would make the due tick spin.
  - Alternative: have the Mutations `SyncError` path leave `sync_deadline` as set and add a tick-driven `PassAction::Mutations` for synthetic.
  - Either way, update the KD-1 wording.

**2. NIT – `sync.rs:746-775` (`load_search_conversation`)**
- Search is meant to be cached only, but a cache miss in a synthetic session still takes `account_status`, `begin_reply_enrichment`, then `provider.get_thread` and `save_search`.
- After bootstrap, every fixture id is already cached, so this is unreachable in practice. It is a policy hole, though.
- **Fix:** add `if self.inner.policy.cached_only_search() { return Err(MailError::NotFound); }` in the `NotFound` arm, before the provider call.

**3. NIT / risk-low – `sync.rs:1523` against `operations.rs:147-152`**
- Admission uses `policy.mutation_access()`, which is `Ok(true)` for synthetic. The worker's `require_mutation_access` still calls `provider.mutation_access()` directly.
- With the real `SyntheticGmailProvider` they agree. With a decorator provider that returns `false` or `Err`, writes are accepted and then requeued with `PermissionRequired`. Combined with finding 1, they would be stuck.
- **Fix:** acceptable as is. Add a comment that the provider must answer `Ok(true)`, or route `run_one` through the policy.

**4. NIT – `sync.rs:1901`**
- If `provider.get_thread(id)` returns `None` for a preload id, bootstrap silently `continue`s and open succeeds with that conversation missing. Requirement 3 says to fail closed.
- Not reachable with the real provider, since the ids come from the provider's own list.
- **Fix:** return `InvalidProviderResponse`, or `storage_fault("synthetic_bootstrap_missing_thread")`.

**5. NIT (test only) – `sync.rs:3723`**
- `let _ = conversation("conv-01");` exists only to silence an unused import. Drop it and the `conversation` import.
- `fire_periodic_tick` (`:3655`) can pass early. If a worker iteration bumps `test_wait_cycles` before the tick flag is set, the wait finishes without the tick being consumed. This cannot cause a false failure, and the Gmail control half does a real wait.
